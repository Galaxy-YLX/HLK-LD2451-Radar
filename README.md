# HLK-LD2451-Radar

基于 HLK-LD2451 的便携雷达。上位机沿用 `EaiLidar-Viewer` 的同一套方案：纯 C++ 协议层 + Qt6 显示层，绿黑雷达主题。

## 方案设计

| 层 | 位置 | 说明 |
| --- | --- | --- |
| 数据模型 | `src/core/` | `Target`（角度/距离/速度/信噪比 + 直角坐标）、`Scan`（一帧目标） |
| 协议解析 | `src/protocol/` | `parser`（数据帧、ACK 解析 + 命令帧构造）、`frame_assembler`（双帧头字节流组帧）。纯 C++ 无 Qt 依赖 |
| 传输层 | `src/transport/` | `SerialTransport`：Qt SerialPort `readyRead` → 组帧 → 解析 → `scanReady` / `ackReady`；`AckSequencer`：纯 C++ 一问一答状态机（单条快速重发、忽略迟到/重复 ACK） |
| 显示层 | `src/ui/` | `RadarView`：**±15° 扇形视图**，雷达位于底部中心（距离弧、角度刻度、目标统一绿色、速度线段） |
| 应用层 | `src/app/` | `MainWindow`（串口连接、模块命令、目标表格、HUD）、`main`（雷达主题） |
| 测试 | `tests/` | 协议文档 §7 实例帧单测、真实串口样本回放 + ACK 状态机单测（纯 C++ 无需硬件）、`serial_probe.py` 实测工具 |

## 协议要点

- **串口**：模块出厂默认 115200 / 8N1，小端。本软件默认选中 **460800**（索引 `0x0008`）；若模块仍是出厂设置，连接时会自动回退到 115200 等候选波特率（见下文「实测数据流特性」），连上后可改选 460800 并点顶部「应用」完成切换。
- **上报数据帧**：`F4 F3 F2 F1` + 长度(2B) + 帧内数据 + `F8 F7 F6 F5`。帧内数据 = 目标数(1B) + 报警(1B) + N×5B（角度、距离、速度方向、速度值、信噪比）；无目标时长度字段为 0。
- **角度** = 上报值 − `0x80`（°），**距离**单位为米，**速度**单位 km/h。
- **探测角度**（手册 V1.03 性能参数）：水平 **±15°**、垂直 ±7°。协议里的 −128~+127° 只是角度字段编码范围，并非真实波束；视图按 ±15° 绘制扇形，超出该角度的上报目标不在视图中显示（目标表格仍列出全部）。
- **命令 / ACK 帧**：`FD FC FB FA` + 长度(2B) + 帧内数据 + `04 03 02 01`；ACK 命令字 = 原命令字 `| 0x0100`，状态 `0x0000` 成功。
- **配置流程**：使能配置 `0x00FF` → 查询/配置命令 → 结束配置 `0x00FE`，严格一问一答（发一条、等该条 ACK 成功、再发下一条）。单条 ACK 超时 **200 ms**，超时后只重发当前命令（最多 3 次，间隔 80 ms），重试用尽才报错；迟到、重复或无关 ACK 一律忽略，不打断队列。
- **连接握手**：串口打开后**立即**发起「读取固件版本」，只有整条队列（含结束配置）全部 ACK 成功才判定为正常连接并启用查询按钮，避免结束配置失败时模块停留在配置模式而界面误报已连接。握手无响应时自动按 `115200 / 460800 / 256000 / 230400` 依次换波特率重试（跳过当前值），全部失败才断开并提示检查端口与波特率，避免把任意串口设备误认为 LD2451。校验期间数据帧仍会刷新视图，但状态栏保持校验提示。串口被拔出等致命错误会发出 `portLost`，界面自动断开清理。

## 实测数据流特性（2026-11-05，`/dev/ttyACM0` @ 460800）

用 `tests/serial_probe.py` 在真机上录制的样本，已固化到 `tests/stream_test.cpp` 做回放回归：

| 项目 | 实测结果 |
| --- | --- |
| 空闲上报 | 每约 700 ms 一个 10 B 空帧 `F4 F3 F2 F1 00 00 F8 F7 F6 F5`（1.43 fps，间隔 687~708 ms），无垃圾字节 |
| 分片 | 每次 `read` 恰好一帧（10~22 B），无跨帧半帧；进入配置模式后暂停上报，只回 ACK |
| ACK 往返 | 10~62 ms；固件版本 ACK 长度字段实测为 `0x0C`（12 B），文档 §5.7 的 `0x0B` 确属笔误 |
| 单条命令丢失 | 偶发某条命令无 ACK，但**后续命令正常应答**；10 轮完整握手中 2~5 轮命中 |
| 无重发 | 8/10 轮成功，平均 217 ms；旧版实现一旦失败还要等 1~2 s 超时才提示 |
| 单条 3 次重发 / 180 ms 超时 / 60 ms 间隔 | 15/15 轮成功，平均 202 ms（重发会带来重复 ACK） |
| 打开串口后延时 | 0 ms 即可正常应答（2/2），旧版固定等 400 ms 无收益 |
| 波特率不匹配 | 其它 7 个候选波特率下均为纯乱码，无有效帧 |

据此做的改动：取消 400 ms 启动延时、ACK 超时 1~2 s → 200 ms、整条流程重跑 → 单条快速重发、迟到/重复 ACK 忽略、整条握手队列成功才判定连接、自动波特率回退；组帧器加入 4 KB 缓冲上限、坏长度字段快速重同步（不再等凑满声明长度）、帧尾恢复前优先保留后续完整帧。

## 构建与运行

```bash
cmake -S . -B build -G Ninja
cmake --build build -j4
ctest --test-dir build --output-on-failure   # 协议单测 + 真实样本/状态机单测
./build/ld2451_viewer                        # 连接串口后显示实时目标
./build/ld2451_viewer --demo                 # 无硬件时用模拟目标演示显示效果

# 真机数据流实测（仅诊断用，需要 pyserial）
python3 tests/serial_probe.py --seconds 5 --dump sample.bin  # 被动采集并统计
python3 tests/serial_probe.py --scan                          # 扫描模块实际波特率
python3 tests/serial_probe.py --rtt --rounds 10               # 握手 ACK 时延与重发成功率
```

Fedora 上打开 `/dev/ttyUSB0` 需先加入 `dialout` 组：`sudo usermod -aG dialout $USER`，重新登录后生效。

界面说明：演示模式只通过启动参数 `--demo` 进入（界面上无演示入口）；固件版本与模块参数信息显示在视图左上角状态文字下方，检测参数按每项一行显示（最远距离、检测方向、最小速度、无目标延迟、累积触发、信噪比阈值）；量程/最远距离、运动方向、速度门、左右镜像、点大小、速度线段、矢量时长、数值标签均可在界面调整。

右侧模块参数区包含「量程 / 最远距离」下拉（同时表示视图显示半径）、「运动方向」下拉（只检测远离 / 只检测靠近 / 均检测）和「速度门」输入（最小运动速度 0~120 km/h）。**无需「应用」按钮**：任一控件变化经 300 ms 防抖后，即通过 `0x0002` 自动下发前 3 字节，第 4 字节「无目标延迟」保持读回的原值不变，走「使能配置 → 写入 → 结束配置」的 ACK 队列。连接握手通过固件版本校验后会自动读取一次参数，填充控件与 HUD；写入成功后也会自动回读，用模块返回值刷新左上角参数显示。读取参数回同步控件时会抑制自动下发，避免形成循环；参数尚未就绪时会提示稍候或手动点「读取参数」。矢量时长为下拉选择 **1~10 s，间隔 1 s**（默认 1 s）；速度线段长度 = `速度(km/h) / 3.6 × 矢量时长(s)` 米，表示目标在该时长内的径向位移，方向仍为靠近指向雷达、远离指向外。

顶部「波特率」下拉为连接与模块设置共用：连接前它决定本地串口波特率；连接后改选目标值并点「连接 / 断开」右侧的「应用」，按协议发送「使能配置 → 设置波特率 `0x00A1` → 重启模块」，等全部 ACK 成功后软件本地串口同步切换到该值。协议规定新波特率在模块重启后生效，因此流程中附带重启命令；切换期间雷达数据会短暂停顿。

## 已知协议歧义（见 `参考文件/LD2451串口通信协议文档.md`）

1. **速度方向定义自相矛盾**：§6.2 字段说明为 `0x01` 靠近、`0x00` 远离；§7 示例解析却把 `0x00` 解释为靠近。解析器统一按 §6.2 执行（见 `src/protocol/parser.cpp` 中 `Target::approaching` 的赋值），不再提供切换；若实测相反，需修改该处判断。
2. **固件版本 ACK 长度字段笔误**：§5.7 示例长度字段为 `0x0B`，但帧内数据实为 12 字节；实测硬件发送的是正确的 `0x0C`。组帧器在帧尾校验失败时先检查后面是否已有完整帧（避免吞帧），再于 ±4 字节内重新定位帧尾，解析器按整帧长度推断帧内数据，因此两种写法都能正确解析。
3. §7 示例中目标 2 的距离字节原文误印为 `IE`，实为 `1E`（30 m），协议文档已勘误。
